## Observation
For this layout/CSS story the plan prescribed an exact griffel mechanism as if settled — `searchBox: { width: '100%', maxWidth: '400px' }` with `toolbarLeft` an explicit non-goal — and a testing must-cover expecting the narrow-viewport box width to be GREATER than the wide-viewport width. Both were wrong and only surfaced when the code was run in a real browser: `width: 100%` resolves against the shrink-to-fit `toolbarLeft` (which has no flexGrow) and rendered the box at ~173px, and a narrow box cannot exceed a wide box when a fixed max-width cap holds at wide. The working fix required growing `toolbarLeft` and flex-growing the box (touching the file the plan fenced off as a non-goal). Cause: planning a CSS/flex layout change by prescribing a specific untested mechanism — rather than the intended behavior plus a real-browser verification — bakes an unvalidated implementation into permanent plan documentation, and an acceptance/test expectation stated without a quick logical sanity check can be self-contradictory (narrow > wide vs a max cap). The jsdom-vs-real-browser rule in testing.md already covers *verifying* visual acceptance in a browser; the gap here is at plan time, where the mechanism and the test's expected outcome were fixed without that verification.
